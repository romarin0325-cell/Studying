# Card RPG 코딩 가이드

이 문서는 처음 코드를 보는 사람이 “어디를 수정해야 하는가”를 빠르게 판단하기 위한 규칙입니다. 기능의 정답은 브라우저 동작이며, 구조 개선 때문에 기존 동작이나 저장 데이터가 바뀌면 안 됩니다.

## 먼저 읽을 파일

1. 화면·버튼·이미지 문제: `index.html`
2. 저장·미션·모드·보상 문제: `rpg_features.js`
3. 턴 진행·스킬 실행 문제: `battle_runtime.js`
4. 스탯·대미지·특성·효과 계산 문제: `logic.js`
5. 카드·적·스킬 문구 문제: `data.js`
6. Lumi/Gemini 문제: `api.js`

전체 연결은 `card_game_structure.md`, 이번 정리의 판단 근거와 예외는 `REFACTORING_REPORT.md`에 있습니다.

## 책임 경계

| 위치 | 넣어야 하는 처리 | 넣지 말아야 하는 처리 |
|---|---|---|
| `data.js` | 카드·적의 정적 수치, ID, 표시 문구 | DOM 조작, 저장, 턴 진행 |
| `logic.js` | 순수 계산, 효과 핸들러, 저장 형식 보정 | 화면 표시, 모달 열기 |
| `battle_runtime.js` | 전투 상태 변경, 턴 순서, 스킬 실행 | 카드 목록 DOM 생성 |
| `rpg_features.js` | 런/전역 상태와 모드·미션 규칙 | 미션 목록 DOM 작성, 이미지 경로 결정 |
| `index.html` | 조립, DOM, 사용자 이벤트, 이미지 모델 | 새 전투 공식 |

추가된 클래스는 세 개이며 역할을 섞지 않습니다.

- `SaveDataMigrator`: 런 저장 정규화와 직렬화만 담당합니다.
- `ImageAssetManager`: 이미지 소스·로드·실패 처리를 담당합니다. 프로젝트 제약상 반드시 `index.html`에 둡니다.
- `MissionView`: 전달받은 값으로 미션 DOM만 그리며 저장 상태를 바꾸지 않습니다.

`RPG` 안의 `executeSkill`, `calcDamage`, `applySkillEffects` 같은 메소드는 기존 HTML/콘솔 호출을 위한 호환 어댑터입니다. 새 전투 로직을 이 래퍼에 작성하지 말고 `BattleRuntime` 또는 `Logic`에 작성합니다.

## 이름과 서식

- 앱 JavaScript는 들여쓰기 4칸, 작은따옴표, 세미콜론을 기본으로 합니다.
- 런타임 변수·메소드는 `camelCase`, 클래스는 `PascalCase`, 상수는 `UPPER_SNAKE_CASE`를 씁니다.
- 조회는 `get...`, 불리언 판정은 `is...`/`has...`/`can...`, 화면 열기·닫기는 `open...`/`close...`, DOM 그리기는 `render...`, 저장 형식 변환은 `normalize...`/`serialize...`로 시작합니다.
- 메소드명에는 구현 방식보다 결과를 씁니다. 예: `renderMissionView`, `getCurrentDateKey`.
- 저장된 레거시 필드의 `snake_case`는 예외입니다. 보기 좋게 바꾸는 것만으로 이름을 변경하면 안 됩니다.
- 카드·아티팩트·모드·미션·버프 ID는 표시 문자열이 아니라 영속 식별자입니다. 이름 변경은 마이그레이션과 회귀 테스트가 있을 때만 허용합니다.

## 주석 규칙

좋은 주석은 코드가 보장해야 하는 이유나 제약을 설명합니다.

```js
// Prevent in-memory defaults from overwriting disk data before the first load.
```

피해야 할 주석은 변경 이력만 말하는 `Fix:`, `버그수정`, `User request`, 코드 내용을 그대로 번역한 설명입니다. 변경 이력은 Git에 남기고, 주석에는 “왜 이 순서/예외가 필요한가”를 남깁니다.

## 저장 데이터 규칙

다음 키는 이름을 바꾸지 않습니다.

- `cardRpgSave`
- `cardRpgGlobal`
- `cardRpgVocab`
- `cardRpgCollocation`
- `cardRpgCollocationDetails`
- `cardRpgApiKey`
- `cardRpgRecords`
- `fortuneCookieLastUsedDate`
- `fortuneCookieLastResult`

런 저장을 읽을 때는 `SaveDataMigrator.normalizeRunState`, 쓸 때는 `serializeRunState`를 거칩니다. 규칙은 다음과 같습니다.

1. 현재 또는 구버전 스키마에서 알 수 없는 최상위·중첩 속성은 삭제하지 않습니다. 단, 실제 카드 ID 목록처럼 검증 함수가 있는 필드는 현재 유효한 값만 남깁니다.
2. 현재 코드보다 높은 `saveSchemaVersion`은 추측해서 낮추거나 열지 않습니다. 원본을 유지하고 불러오기를 중단합니다.
3. 누락되거나 잘못된 배열·중첩 구조만 안전한 기본값으로 보정합니다.
4. UI 전용 `currentToeicSession`만 직렬화에서 제외합니다.
5. JSON 손상과 구조 오류를 “저장 없음”으로 취급하지 않습니다. 손상 JSON은 원본을 유지하고 복구용 사본을 남깁니다.
6. 글로벌 해금 데이터는 기존 백업과 손상 복구 경로를 유지합니다. 복구본을 주 저장소에 실제로 쓴 뒤에만 성공으로 처리하며, 실패하면 이어하기·미션·검색 변경을 중단합니다.
7. `cardRpgRecords`의 `최대 스테이지: N` 문자열은 현재 파서가 읽는 저장 형식입니다. 표시 문구처럼 보여도 임의로 바꾸지 않습니다.
8. 학습 진도는 런 저장과 전용 키에 중복되어 있으며, 로드 시 전용 키가 우선합니다. 마이그레이션 없이 한쪽을 제거하지 않습니다.

새 저장 필드를 추가하면 기본값, 구버전 누락 보정, 알 수 없는 필드 보존, 직렬화 제외 여부를 `verify_card_refactor.js`에 테스트합니다.

## 이미지 규칙

이미지 모델은 메인 코드인 `index.html`의 `ImageAssetManager`입니다.

- 정적 이미지는 `data-image-src`, 동적 카드/적 이미지는 `ImageAssets.load` 또는 `createPortrait`을 사용합니다.
- 데이터에 `imageFile`이 있으면 우선 사용하고, 없으면 기존 호환 규칙인 `${entity.name}.png`를 사용합니다.
- `onerror="this.src=''"`, 빈 `src`, 각 화면의 개별 파일명 조합을 추가하지 않습니다.
- 이미지가 없을 수 있으므로 로딩 실패는 게임 초기화 실패가 아닙니다. 관리자가 깨진 아이콘과 필요 시 부모 영역을 숨깁니다.
- 전투 화면처럼 반복 렌더링되는 곳에서도 같은 소스는 다시 요청하지 않습니다.

## 모바일 순차 로더 규칙

`index.html`의 순차 로더는 모바일 `file://` WebView 호환을 위해 유지합니다. 클래스나 ES module 로더로 바꾸지 않습니다.

새 스크립트를 추가할 때는 다음을 함께 처리합니다.

1. `scripts` 배열에서 의존 파일보다 뒤에 둡니다.
2. `getMissingRequiredData()`에 실제 준비 완료를 나타내는 전역을 추가합니다.
3. `_scriptLoadComplete` 전에는 버튼을 활성화하지 않습니다.
4. 로드 오류나 모듈 설치 예외는 새로고침 버튼이 있는 사용자 오류 화면으로 남깁니다.
5. `verify_card_mobile.js`의 정상/실패 경로를 통과시킵니다.

## 카드·특성·효과 추가 규칙

`name`은 아직 일부 적 AI와 시너지 트리거가 참조하므로 표시명만 바꿔도 동작이 달라질 수 있습니다. 장기적으로는 `skill.id`를 추가하고 `id` 우선, `name` 호환 순서로 옮겨야 합니다.

새 `effect.type`을 추가할 때는 다음 중 어디에서 처리하는지 하나로 정합니다.

- 대미지 배율·관통 계산: `DAMAGE_EFFECT_HANDLERS`
- 버프·디버프·필드·예약 처리: `SideEffects.handlers`
- 지연 스킬 변환: `buildResolvedDelayedSkill`
- 전투 흐름 자체: `BattleRuntime`

같은 효과를 새 타입과 복사한 분기로 다시 만들지 말고 기존 핸들러를 재사용합니다. 기존 타입명이 이미 데이터에 있으면 즉시 삭제하기보다 별칭을 같은 공통 처리에 연결합니다. 베히모스 두 타입이 이 호환 방식의 예입니다.

현재 `val`은 퍼센트, 확률, 배율을 모두 나타내는 레거시 필드입니다. 기존 데이터는 유지하되 새 복합 효과는 `chance`, `mult`, `ratio`, `threshold`처럼 의미가 드러나는 필드를 우선하고, 핸들러와 테스트를 같이 추가합니다.

## 합연산·곱연산 규칙

현재 공식은 단계별로 일관되지만 단계 사이가 모두 같은 방식은 아닙니다.

1. 초기 자기 특성과 배치 특성을 곱하고 정수화합니다.
2. 같은 파티 보너스 범주의 `%`는 먼저 합한 뒤 한 번 곱하고 정수화합니다.
3. peer 보너스와 혼돈 축복은 앞 단계 결과에 다시 곱합니다.
4. 전투 중 필드/특성 보너스와 디버프는 같은 스탯 계수에 가감한 뒤 기본 스탯에 곱합니다.
5. 스킬의 “배율 추가”는 `ctx.mult +=`, “N배”는 `ctx.mult *=`입니다.
6. 특성 대미지 보너스는 `(val - 1)`을 합한 뒤 `skillMultiplier * (1 + traitBonus)`로 적용합니다.
7. 치명·속성·방어·가드 단계를 거쳐 최종 정수화합니다.

따라서 같은 `+30%`라도 자기 특성, 파티 합산, 런타임 축복 중 어느 단계인지에 따라 결과가 달라집니다. 한 스킬의 효과 배열에 `+=`와 `*=` 배율을 섞으면 순서 의존성이 생길 수 있으므로 피하고, 꼭 필요하면 계산 예시를 설명과 테스트에 고정합니다. 치명타 확률과 회피율은 퍼센트포인트 합산입니다.

방어 관통과 상태 적용 시점에는 레거시 예외가 있습니다. 대부분 관통은 원 방어력 기준 합산이지만 꿈의형태 계열은 유효 마방 기준이며, 일반공격 특성 디버프는 피해 전·스킬 데이터의 일반 `debuff` 효과는 피해 후에 적용됩니다. 베히모스처럼 별도 특성 훅으로 먼저 적용하는 스킬은 예외입니다. 밸런스 결정을 하지 않은 채 공통화하지 않습니다.

Guardian은 이름이 정확히 `가드`인 스킬만 75% 감소로 강화합니다. `디바인아머`처럼 같은 `guard` 상태를 쓰는 다른 스킬은 50%입니다. 두 효과의 남은 턴은 별도로 추적합니다.

## 완료 전 검사

```powershell
npm run verify
```

이 명령은 문법, 저장/구조, 전투 회귀, 모바일 `file://` 로더·이미지·레이아웃, 스페셜 미션 흐름을 검사합니다. 실제 Android WebView나 새 실제 이미지 파일을 추가했다면 해당 기기에서도 한 번 확인합니다.
