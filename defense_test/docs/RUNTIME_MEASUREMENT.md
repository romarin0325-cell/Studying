# Star Garden 전투 실행 비용 관측

2026-10-05, `codex/star-garden-media-efficiency`, 기준 `71f3d4c`의 전투 엔진을 수동 측정했다. **엔진 최적화 후보는 적용하지 않았다.** 반복문 후보의 고부하 평균 개선은7.16%이고 한 시드에서는3.51% 느려졌다. 현재 비용이 작고 일관된 개선을 입증하지 못했으므로 기존 상태 효과·편성·저장·피해 규칙을 유지한다. 이 관측은 새 테스트, CI 작업, 정기 성능 게이트를 추가하지 않는다.

## 방법과 범위

Windows x64, AMD Ryzen7 4800H(8코어/16스레드), Node24.13.1에서 실제 `step(.05)`를600번 호출해30초를 시뮬레이션했다. 별도 상태에서3초 준비 실행 후 원래 fixture를 다시 복원했다. 시드1234·98765·606606, 각3회이다. `restore(serialize(state))`가 허용하는 전투 상태만 사용했다.

| 조건 | 유닛 | 적 최대 | 장판 최대 | 상태 출처 최대/적 | 감속 출처 최대/적 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 시작 전투 | 6 | 9 | 0 | 4 | 6 |

시작 전투는 기본 편성에서 무료 소환3회를 추가하고 실제 웨이브를 진행한다. 나머지는 머쉬룸킹·화염의현자·명탐정·눈토끼·팬텀을 배치하고, 실제 생성·공격·장판·필살기 경로로 독·화상·노출·감속·빙결을 발생시킨다. 적 HP1e9와 낮은 이동속도로 계측 중 전투를 유지했다. 초기 독립 장판은 일반 규모12개, 고부하75개이며 실제 위력·반경·시간·시전자 UID를 가진다. 계측 외부에서8초마다 게이지를 재충전해5종 필살기를 다시 시전한다. 따라서 고부하는 지속 효과를 집중시킨 합성 워크로드이며 스토리 난이도나 자연 플레이 빈도의 추정이 아니다.2048개 출처 같은 저장 한도를 실제 플레이 상태로 꾸미지 않았다.

기존 엔진과 후보 복사본은 각각 별도 Node 프로세스에서 실행했다. 동일 fixture·시드·반복 번호를 비교했지만 JIT 준비, GC, 다른 데스크톱 작업의 영향을 완전히 제거한 통제 실험은 아니다. 다음 표는 각3회에서 얻은 **step 평균/p95/p99의 산술평균**이다. 여러 실행의 모든 표본을 합친 백분위가 아니다. 단위는ms이다.

## 병목과 기각한 후보

기존 복사본에만 호출 계수와 Node CPU profiler를 넣어 시드1234의30초를 추가 관측했다. 계수 삽입 실행의 시간은 위의 비계측 실행과 섞지 않는다.

| 조건 | syncStatuses | syncSlows | activePoison 정렬 | damage | addStatus | statusState |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 시작 | 8,265 | 8,307 | 2,609 | 203 | 34 | 0 |
| 일반 규모 | 65,297 | 61,989 | 9,600 | 30,608 | 2,671 | 0 |
| 고부하 | 468,592 | 402,922 | 60,000 | 214,576 | 35,883 | 0 |

CPU 표본은 `tickEnemyStatuses`, `activePoison`의 정렬·비교, 반복 상태 정리, GC에 집중됐다. 이 엔진 전용 계측에서는 UI의 `statusState`를 호출하지 않으므로 이 표로 UI 조회 비용을 판단하지 않는다. 첫 고부하 비계측 실행의 heap 시작8.0MiB/표본 최대25.2MiB/종료11.7MiB, Node가 보고한 GC91회·31.4ms였다. heap 최대는60step마다 읽은 표본의 최대이며 프로세스 전체 최대나 휴대전화 메모리 요구량이 아니다. 별도 반복 실행에서는 GC/JIT에 따라 값이 달라졌다.

임시 후보는 상태·감속 배열을 같은 순서로 제자리 압축하고, 독의 기존 `power→until→source` 정렬을 유지하면서 `flatMap` 대신 상위40스택이 채워질 때 종료하는 반복문을 사용했다. 새로운 캐시나 만료 규칙은 추가하지 않았다. **27개 matched 실행 모두 최종 직렬화 전체의SHA256과 실제 누적 피해가 기존과 완전히 같았다.** 그러나 고부하에서 일관된20% 수준의 개선을 보이지 않았고 시작 전투는 대체로 악화했다. 후보를 제품에 넣지 않았다.

독 활성40스택·독 원자료 보존, 상태/감속 출처 배열 각각2048개 복원 허용, 장판75개, 출처별 만료·소유자 귀속, 제어 적분, 덱·저장 버전·피해 공식을 변경하지 않았다. 현재 규칙은 [STATUS_RULES.md](STATUS_RULES.md)에 그대로 유지한다.

## 실제 브라우저의 고부하 그리기

현재 단일HTML의 임시 복사본에서 앱이 호출하는 `renderer.draw` 한 곳과 그 프레임의requestAnimationFrame 콜백만 시간 계측했다. 실제 저장을 정상 복원해 이어하기 버튼으로 진입했다. Chromium147.0.7727.15 headless,390×844 터치 viewport, DPR2, 기본 화질의 캔버스 DPR1.5,1배속, 자동 전투OFF이다.1초 준비 후30.04초 동안 실제 앱 루프가30.05초 전투를 진행했고903회 그렸다.

| 관측 대상 | 평균 | p95 | p99 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| renderer.draw 동기 호출 | 24.03ms | 31.70ms | 33.30ms | 38.10ms |
| 그리기를 수행한 앱 프레임 콜백 | 24.89ms | 32.80ms | 34.80ms | 41.10ms |

유닛20/적100은 유지됐고 장판31~75, 상태 출처26~51/적, 감속4~8/적, 입자0~120, 충돌 연출0~11였다. 브라우저 관측에서는 인위적으로 게이지를 재충전하지 않고 실제 앱을 진행했다. 페이지 오류0, HTTP 요청0, 저장 실패0이다. 첫 상태의 장판75개를 포함해 실제 공격으로 늘고 줄어드는 장판을 그렸다.

이 조건에서는 동기 그리기 비용이 Node의 전투 계산보다 컸다. 다만 서로 다른 런타임의 시간을 직접 합산하거나,903회/30초를 기기 성능의 최대FPS로 해석할 수 없다. 이 값은 지정된 화질·렌더 주기·고부하 fixture의 데스크톱 headless 관측이다. GPU 합성, Android/iOS 실기기FPS, 발열·배터리·장기 성능을 입증하지 않는다. 현재 결과만으로 전투 규칙이나 연출을 추가 변경하지 않았다.

수동 스크립트·복사본·JSON·CPU profile·스크린샷은 Git에서 무시하는 `defense_test/test-results/runtime-bench/`에 남겼다. 주 실행은 `manual.mjs`, 후보 생성은 `generate-loops.mjs`, 브라우저 관측은 `browser-render.mjs`이며 어느 파일도 정기 검증에 연결하지 않았다.
