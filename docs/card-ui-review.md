# Card 세 UI의 기능과 흥미 검토

## 비교 기준

수정 전 기준은 `main` 커밋 `bfb5b8c888b835d6e10af06903c68d8c18d4daa0`이다. 여기서 레거시는 삭제된 옛 폴더의 오래된 게임 로직이 아니라, **최신 `card/game/index.html`의 기존 화면**을 뜻한다. 레거시 화면을 최신 공통 소스로 빌드하면 과거 데이터로 되돌아가지 않고 UI만 비교할 수 있다.

아래 기능 비교표는 수정 전 코드 감사 결과이며, 이번 작업의 완료 상태는 다음 절에 따로 기록했다. 흥미에 대한 평가는 소스, 설계 문서, 저장소에 있는 화면 캡처를 근거로 한 가설이며 사용자 행동 데이터로 확인한 인과관계는 아니다.

## 이번 작업의 반영 결과와 실행 방법

레거시·아스트라·루멘 모두 원본 로더에 선언된 동일한 19개 공통 모듈을 읽도록 빌더를 맞췄다. 이후 공통 카드·학습 데이터나 기능 모듈을 추가할 때 UI별 빌더 목록이 따로 뒤처지는 문제를 줄였다. 레거시는 최신 공통 규칙을 유지하면서 원래의 어두운 UI로 실행되는 독립 HTML로 복원했다.

- 세 UI에서 같은 `CardProgressTransfer`로 여정·영구 해금·학습·모드 기록을 내보내고 가져온다. API 키는 제외한다.
- 레거시와 아스트라에 최대 10문제 연속 도전과 빈 파티 자리 자동 선택·다음 빈자리 이동을 추가했다. 기존 루멘의 흐름과 연출은 유지한다. 도전 비용·정답 보상은 원본 게임 처리를 사용한다.
- 전체 화면 버튼은 세 UI 모두 우상단에 있다.
- 루멘의 작은 세로 화면에서 사라지던 다음 상대와 경로를 유지했다. 상대 영역에 최소 96px를 확보하고 파티를 압축하며, 더 좁은 320px 화면에서는 필요한 내용을 스크롤해 접근한다.

저장소 루트에서 세 UI를 함께 빌드하고 검증한다.

```sh
npm ci
npm run build:card-uis
npm run test:card-uis
```

| UI | 실행할 단일 HTML |
| --- | --- |
| 레거시 | [DREAMWEAVER-Legacy.html](../card_legacy/dist/DREAMWEAVER-Legacy.html) |
| 아스트라 | [DREAMWEAVER-Astra.html](../card_astra/dist/DREAMWEAVER-Astra.html) |
| 루멘 | [DREAMWEAVER-Lumen.html](../card_lumen/dist/DREAMWEAVER-Lumen.html) |

초상화 PNG와 음악·리스닝 MP3는 기존 파일명으로 HTML 옆에 둔다. 코드·데이터·CSS는 HTML에 포함되지만 개인 미디어를 파일 안에 합치지는 않는다.

같은 진행도로 비교하려면 현재 UI에서 먼저 여정을 저장한 뒤 기록 파일을 내보낸다. 레거시는 타이틀 또는 게임 메뉴의 **기록 옮기기**, 아스트라·루멘은 **설정 → 기록 내보내기/가져오기**를 사용한다. 다른 UI에서 파일을 가져와 확인한 후 이어가기를 선택한다. 파일 경로와 호스트가 다르면 브라우저 저장 공간도 다를 수 있으므로 자동 동기화를 전제하지 않는다.

### 확인한 결과와 범위

세 빌드의 실제 실행 데이터를 비교해 카드 161종, 단어 762개, 연어 130개, 문법 35강, TOEIC 78개, 리스닝 36개가 같고, 소환 확률과 저장 키도 같음을 확인했다. 항목 수뿐 아니라 데이터 내용의 해시를 비교했다.

공통 브라우저 검증은 320×568·360×640·390×844에서 통과했다. 같은 기록의 내보내기·가져오기·재로드·이어가기, 연속 도전의 정답/오답 비용과 카드 수·중단·모드 제한, 빈자리 자동 이동, 미션·세트 편집, 전투 스킬 4개의 접근성, 우상단 전체 화면 진입·종료를 확인했다. 브라우저 예외와 외부 요청은 없었다. 기존 아스트라·루멘 smoke 검사와 변경 감지 선택기의 35개 픽스처도 통과했다.

검증 환경의 Chromium이 `file://` 탐색을 막아, **배포용 단일 HTML 그대로를 loopback HTTP로 제공**해 검사했다. 따라서 이 환경에서의 직접 파일 실행은 확인하지 못했다. 실제 모바일 기기·소프트 키보드·개인 초상화 및 음원 전체·실제 Gemini API 응답도 미확인이다. 자동 검증이 실제 기기의 모든 동작이나 흥미를 보장하지는 않는다.

## 수정 전 루멘과 아스트라의 진행도는 같았는가

**게임 내용과 저장 구조는 같고, UI의 구현 범위는 다르다.** 두 빌더는 같은 `card/game/`에서 카드·학습 데이터, 전투·모드·보상 규칙, 저장 마이그레이터, 컨트롤러를 읽는다. 어느 쪽에만 신규 카드나 학습 문제를 별도 복제해 관리하는 구조가 아니다. 반면 루멘의 연속 도전 소환과 전투 연출은 루멘 전용 어댑터에 있다.

| 비교 항목 | 레거시 원본 화면 | 아스트라 | 루멘 |
| --- | --- | --- | --- |
| 카드·보너스·스페셜·초월 카드 데이터 | 공통 | 공통 | 공통 |
| 단어·연어·문법·TOEIC·리스닝 데이터 | 공통 | 공통 | 공통 |
| 모드·전투 계산·보상·미션·영구 해금 | 공통 | 공통 | 공통 |
| 여정 저장·전역 기록·최고 기록의 키와 형식 | 공통 | 공통 | 공통 |
| 한 장 일반 소환 / 한 문제 도전 소환 | 있음 | 있음 | 있음 |
| 최대 10문제 연속 도전 | 없음 | 없음 | 있음 |
| 빈 파티 자리 자동 선택·다음 빈자리 이동 | 수동 | 수동 | 있음 |

| 전체 도감의 영구 해금 수·획득 조건 강조 | 기본 정보 | 있음 | 이번 여정 보유 수 중심 |
| 기록 JSON 내보내기·가져오기 | 공통 어댑터 미적용 | 있음 | 있음 |

| 미션 보상 그림·진행 막대·편집 화면 재구성 | 기본 화면 | 공통 화면 일부 개선 | 추가 개선 |

편성 검색·열 수·표현 방식은 비교 UI의 차이로 남길 수 있다. 연속 도전, 기록 이동처럼 할 수 있는 일 자체가 달라지는 항목은 공통화해야 동일한 기능을 두고 UI를 비교할 수 있다. 연출의 차이는 카드나 보상을 더 지급하는 차이가 아니다.

개인 진행 기록도 구분해야 한다. 같은 저장 키를 사용해도 브라우저·파일 경로·호스트가 달라지면 저장 공간이 달라질 수 있다. 세 파일을 열었다고 자동으로 같은 여정이 나타나는 것은 아니다. 여정을 먼저 저장하고 기록 JSON을 내보내 각 UI에 가져오는 방식으로 같은 상태를 맞춘다. 여정뿐 아니라 영구 해금·미션·모드별 최고 기록·학습 오답 기록도 함께 비교한다.

- [Astra 어댑터](../card_astra/src/edition.js)의 `acquisition`, `decorateCollection`, `decorateDetail`은 영구 해금과 획득 경로를 드러낸다.

## 화면이 좋아져도 흥미가 줄어들 수 있는 이유

가독성·조작 편의와 계속하고 싶은 마음은 서로 다른 결과다. 지금 변경은 화면의 정리와 이동 속도에는 많은 투자를 했지만, **다음에 갖고 싶은 것·이번 선택으로 달라지는 것·방금 얻은 성취**를 드러내는 정도는 화면마다 다르다. 다음 여섯 가지를 우선 검증할 만하다.

### 1. 로비가 명확해진 만큼 탐색할 여지도 작아졌다

[Lumen 설계 노트](../card_lumen/docs/DESIGN.md)는 출전을 유일한 주 행동으로 두고, 기록·카드풀·저장 등의 관리를 설정에 모은다고 명시한다. 원본 로비는 덱·카드·도서관·축복·전투·메뉴를 직접 보여준다. 새 로비는 다음 전투를 하기에는 명확하지만, 목표가 아직 없는 플레이어에게는 매번 출전만 반복하는 화면으로 보일 수 있다.

버튼을 다시 모두 늘리기보다는 현재 파티와 연결되는 목표 한 가지를 로비에 보여주는 편이 적절하다. 예를 들어 실제 미션에서 읽은 다음 해금 카드와 남은 조건, 현재 보유 카드로 바꿀 수 있는 조합을 제시한다. 이미 완성한 파티에도 같은 일반 안내 문구만 반복되는지 확인한다.

### 2. 소환을 빠르게 묶으면서 짧은 기대와 보상이 뒤로 밀린다

연속 도전은 정답마다 원본 소환을 실행하고 공개만 마지막으로 미룬다. 학습을 이어가기에는 편하지만 한 문제를 풀고 카드를 확인하는 짧은 보상 순환은 줄어든다. 카드가 나의 선택이나 다음 전투에 어떤 영향을 주는지 확인하기 전에 다음 문제가 시작될 수도 있다.

한 장 도전을 계속 선택할 수 있게 유지하고, 연속 결과에서는 새 카드·중복·현재 파티와의 관계를 쉽게 판단하게 한다. 문제마다 강제로 연출을 늘리거나 일반 소환의 확률을 바꾸기 전에, 사용자가 한 장 도전과 연속 도전 중 무엇을 다시 선택하는지 비교한다.

### 3. 세련된 프레임이 캐릭터의 자리를 대신할 수는 없다

[Astra 검토 화면](../card_astra/docs/REVIEW.md)은 개인 초상화가 없어 같은 카드 뒷면을 사용한다. [Lumen 미리보기](../card_lumen/README.md)는 별빛 정원 그림을 임시로 사용했다. 따라서 저장소의 두 미리보기만 보고 흥미 차이를 UI 때문이라고 판단하면 이미지 조건이 섞인다. 같은 뒷면 세 장은 이름과 수치가 달라도 시각적으로는 동료 셋의 차이가 약하다.

세 UI에 같은 실제 초상화 폴더를 연결한 후 비교해야 한다. 실제 사용자에게 이미 초상화가 잘 보인다면 이 가설의 우선순위는 낮다. 초상화 누락 자체와 캐릭터에 대한 애착 부족도 별개로 확인한다.

### 4. 장기 진척이 실제 데이터보다 덜 보이는 화면이 있다

Astra 도감은 영구 해금 수와 카드별 획득 조건을 보여준다. 수정 전 Lumen 상세는 주로 이번 여정의 보유 수를 보여준다. Lumen의 보상 카드·미션 막대는 개선되었지만 미션 창을 열어야 보인다. 전투나 학습을 반복해도 무엇에 가까워지는지 놓치면, 매번 같은 여정을 처음부터 돌리는 느낌이 커질 수 있다.

이번 여정 스테이지, 계정의 영구 해금, 학습 정답 수를 서로 구분해 이름 붙인다. 로비에서는 그중 지금 행동으로 달라질 목표 하나를 드러내고, 보상 직후에는 실제로 바뀐 해금이나 조합을 연결한다. 표시용 진척을 새로 만들 필요는 없다.

### 5. 작은 세로 화면에서는 흥미를 주는 정보부터 사라진다

수정 전 Lumen의 `lumen.css`는 다음 상대 영역 높이가 190px 이하이면 스킬, 140px 이하이면 경로, 104px 이하이면 상대 미리보기 전체를 숨겼다. 버튼을 누를 수 있어도 보스까지의 거리와 상대 캐릭터가 보이지 않았다. 이번 작업에서는 상대와 경로를 유지하도록 수정했다. 이 사례처럼 레이아웃이 정상이라는 판정만으로는 흥미를 주는 정보의 손실을 발견하기 어렵다.

작은 화면에서는 초상화를 줄이더라도 상대 이름·보스 여부·남은 거리 같은 판단 정보의 최소 표현이 남는지 본다. 모바일 검증에는 버튼 잘림뿐 아니라 다음 목표를 읽을 수 있는지도 포함한다.

### 6. 새 연출은 같은 선택과 보상을 계속 새롭게 만들지는 않는다

게임 규칙과 학습 데이터가 같은 것은 호환성에 유리하다. 그러나 화면이 달라져도 플레이어가 고르는 스킬·편성·학습 목적이 늘 같다면 첫인상의 개선 후 반복이 더 선명해질 수도 있다. Lumen에 추가된 컷인·돌진·빛 효과는 행동을 전달하지만 그 자체로 새 전술이나 목표를 만들지는 않는다.

효과를 더 추가하기 전에 새 카드 획득 후 편성을 바꾸는지, 다음 상대를 보고 스킬이나 속성을 고려하는지, 학습 보상이 다음 도전에 연결된다고 이해하는지 본다. 연출 건너뛰기와 모션 감소를 존중하고, 장기적으로 반복되는 소요 시간도 비교한다.

## 세 UI를 비교하는 짧은 방법

1. 같은 브라우저·화면 크기·기록 JSON·초상화·음원으로 시작한다. 테마 밝기와 모션 설정도 맞춘다.
2. 각 UI에서 소환, 세 자리 편성, 전투, 미션 확인, 학습, 저장을 한 번씩 한다. UI 순서를 바꿔 순서 효과를 줄인다.
3. 조작 시간·오입력·잘림 외에 다음 세 가지를 기록한다: “지금 갖고 싶은 카드와 그 이유”, “다음 전투를 한 번 더 하고 싶은가”, “학습을 자발적으로 한 번 더 여는가”.
4. 흥미 점수와 함께 구체적인 순간을 적는다. 소환 직후, 전투 승리 직후, 로비 복귀 직후 중 어디서 손이 멈추는지가 다음 수정의 근거다.

우선순위는 공통 기능·저장 호환과 모바일 조작을 맞춘 뒤, 같은 자료로 세 UI를 비교하는 것이다. 그 다음에는 장기 목표의 가시성과 획득 카드의 의미를 먼저 실험한다. 사용자 관찰 없이 화면 장식을 더 늘리는 것으로 흥미 저하의 원인을 확정하지 않는다.
